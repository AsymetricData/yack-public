Design notes · Memory model · about 20 minutes

Ownership, without a garbage collector.

Yack is an experiment: a small ML-family language with a syntax its author finds pleasant and simple, compiled through LLVM to native code. Affine and linear types, borrowed from Rust's ownership model, replace the garbage collector; the only ceremony left is what the types force.

01. The starting point

A comfortable ML, without a garbage collector

Yack exists because its author wanted a language with a syntax they find pleasant and simple: the ML family, close to SML and OCaml, with let and val, fun, datatypes, pattern matching, modules and pipes. The goal is a language that feels like home and is comfortable to write, with little ceremony.

Rust shows that ownership can replace a garbage collector: affine and linear types, moves and borrows do the work a tracing collector would otherwise do. Its syntax is felt as verbose and heavy by comparison, so Yack keeps the ownership ideas and drops that weight. The memory model stays checked in the frontend, over a syntax that stays small.

The only ceremony that should remain is what the types force: a move when ownership is transferred, a borrow annotation when a value is read without being taken, a call that consumes a linear value. The borrowing section shows the annotations, and What it costs sets out where they are felt. Yack is an experiment; version 0.2.0 is usable and tested, but it is not presented as production-ready.

No hidden runtime collection. Values are moved, borrowed and dropped according to their declared property. There is no tracing collector and no reference counting; the compiler emits native code, and the ownership information is checked before lowering.

The rest of this page describes the model as it exists in the repository, including the parts that are still rough. It is not a specification of a finished language.

02. Three properties

Copy, Affine, Linear

Every type has a memory property. The property decides whether a value may be duplicated, moved once, or must be consumed exactly once.

PropertyRuleExamples in Yack
Copy May be copied freely. Passing it does not end the original binding. int, bool, unit, a record declared : Copy
Affine Used at most once. It may be moved, or dropped; the compiler inserts the drop when the owner goes out of scope. User types by default, records, datatypes, string, arrays and maps
Linear Used exactly once on every path. It cannot be dropped implicitly; an unconsumed value is a compile error. token, SQLite db and statement, network listeners and streams

A declaration can state the property explicitly:

properties.yack 
type point : Copy = { x : int, y : int }
type buffer : Affine = { size : int }
type handle : Linear = { id : int }
type default_affine = { value : int }

fun main () = ()

This block is a complete, checked file; the empty main only makes the declarations runnable. Without an annotation a user type is Affine. A composite containing a Linear component becomes effectively Linear, and the checker rejects a declared Copy type with non-Copy fields (E3015) or a declared Affine type with a Linear field (E3016). yack types file.yack prints the declared and effective properties.

03. Affine in practice

A move is a transfer of ownership

Affine is the default discipline. Passing an Affine value to a function parameter transfers it: the callee now owns it. The old binding is marked moved, so reading it again is not allowed. If the callee does not pass the value on, the compiler places its drop at the end of the scope.

buffer.yack 
type buffer : Affine = { size : int }

fun grow (buffer : buffer) : buffer =
    { size = buffer.size * 2 }

fun main () =
    let val buffer : buffer = { size = 16 }
        val larger = grow (buffer)
    in print_int (larger.size)
    end

buffer is moved into grow. The parameter is owned by grow; the function reads its Copy field and returns a new record. The old record is dropped by the callee, the new one by main. There is no explicit free in the source.

Using the old binding after the transfer is rejected. Here the value is a Linear token, but the move rule is the same for an Affine record:

use_after_move.yack 
fun main () =
    let val ticket = new_token ()
        val _ = consume_token (ticket)
    in consume_token (ticket)
    end
yack check 
error[E0402]: value `ticket` is used after being moved
  --> use_after_move.yack:4:23
  |
4 |     in consume_token (ticket)
  |                       ^^^^^^
  = note: the value was already transferred to another owner
  = hint: move the use before the transfer, or copy the value if its type is Copy

Partial moves are tracked too. After moving a record field, the parent still exists but that place is uninitialized; using it again is E0402 with the field path in the message. The backend then drops only the fields that remain owned.

04. Linear resources

Some things must be closed exactly once

Affine says “at most once”. Linear says “exactly once, on every path”. An Affine value may be dropped silently; a Linear value may not. This is the property used for resources whose cleanup is observable: a token, a SQLite connection, a prepared statement, a socket.

token_ok.yack 
fun main () =
    let val ticket = new_token ()
        val _ = consume_token (ticket)
    in print_int (1)
    end

Forget the consumption and the program does not typecheck. The error names the value and suggests the missing call:

unconsumed.yack 
fun main () =
    let val ticket = new_token ()
    in print_int (1)
    end
yack check 
error[E0403]: linear value `ticket` is never consumed on this path
  --> unconsumed.yack:2:9
  |
2 |     let val ticket = new_token ()
  |         ^^^^^^^^^^^^^^^^^^^^^^^^^
  = note: values with the Linear property must be consumed exactly once on every path
  = note: leaving it alive is rejected instead of freeing it implicitly
  = hint: consume it with `consume_token (ticket)`
  = hint: or move the consumption after the `if`/`case` so every branch reaches it

Linearity is a declared type property, not a special case for two builtins. A record or datatype can be declared : Linear, and the checker follows it through branches. The SQLite binding in lib/sql/src/Sqlite.yack does this for db and statement:

lib/sql/src/Sqlite.yack 
(* excerpt from lib/sql/src/Sqlite.yack *)
type db : Linear = { handle : int64 }
type statement : Linear = { handle : int64, owner : (borrow db) option }

fun main () = ()

close consumes a db; finalize consumes a statement. Forgetting either on a path is E0403; closing twice or using a closed connection is E0402. A prepared statement also holds a borrow of its database, so close (db) before finalize (statement) is E0501. The traps are pinned by test/sql/forgot_finalize.yack, test/sql/forgot_close.yack, test/sql/close_twice.yack and test/sql/close_with_open_stmt.yack, and documented in docs/sql.md.

No automatic destructors. There is no RAII-style close in the language. The compiler can prove that you forgot close or finalize, but it does not run them for you. The SQLite documentation states the same limit.

The network package uses the same pattern for listener and stream in lib/net/src/Net.yack; the functions are close_listener and close. Linearity here is a discipline over declared handle types: the property is checked by the same ownership analysis that handles moves, not by a separate runtime mechanism.

05. Borrowing

Read without taking ownership

Moving is not always what you want. A function that only reads a record should not take it away from the caller. Yack has borrow for that:

borrow.yack 
type account : Affine = { id : int, balance : int }

fun balance_of (value : borrow account) : int =
    value.balance

fun main () =
    let val account : account = { id = 7, balance = 42 }
        val first = balance_of (borrow account)
        val second = balance_of (&account)
        val moved = account
    in print_int (first + second + moved.balance)
    end

borrow account is a shared borrow; it is Copy, so a function can take it without consuming the owner. &account is the short form of the same expression, and both spellings are accepted. Here the loan ends at the last use of the borrowed value, so account can be moved afterwards. That is non-lexical lifetimes (NLL).

The rules are deliberately local:

  • A borrow operand must be a place: a local variable, or a chain of record fields and tuple indices rooted in one. borrow (f x) is E0500.
  • Shared borrows may overlap; a borrow mut is exclusive and conflicts with any other live borrow of an overlapping place (E0502).
  • Moving the owner while a borrow is still live is E0501; a borrow that escapes the let owning its source is E0507.
  • A function returning a borrow must name its provenance with from (parameter name or 1-based index); an absent or ambiguous origin is E0503.

Two limitations matter for an honest picture. Reading a non-Copy field through a borrow is currently rejected with E0508 (“cannot read non-Copy field name through a borrow”), so an accessor must copy the value out or take the field by another route. And although the syntax accepts borrow mut, mutable borrows are still non-aliasing copies: no operation in the language mutates through a borrow yet. The checks and the conflict rules exist; mutation through them is not implemented.

06. Memory modes

Heap, arenas, and an experimental stack mode

Yack has two allocation modes, selected at build time with --memory=heap (the default) or --memory=stack. The same source can be compiled in either mode; the mode changes the emitted runtime, not a runtime flag.

ModeHow values are releasedStatus
Heap Ownership decides when free is emitted. An arena block batches temporary strings. Default
arena ... in ... end Opens a temporary scope and releases it at end. In heap mode only strings use it; arrays and maps keep their normal drop. Available in both modes
--memory=stack Each activation gets a bump-pointer region; the region is destroyed at return, and free is a no-op. Escaping values must be proven safe or the program is rejected. Experimental
arena.yack 
fun main () =
    arena
        val text = "hello" ^ " " ^ "world"
    in
        print_string (text)
    end

The arena version exists because short-lived concatenations are common in request handling. In heap mode it avoids one malloc and free per temporary string; the block is recycled at end. In stack mode the request arena is part of the region scheme, and a borrow whose owner lives in an arena cannot escape the block (E0703).

Stack mode is the more ambitious half of the experiment. It emits no malloc, calloc, realloc or free from libc for Yack values; allocations come from a region reserved with mmap. The contract is that the compiler must prove a value does not outlive its region, and must reject the program rather than fall back to the heap. The region verifier is still being completed: E0702 covers stores the analysis cannot prove, E0703 covers a borrow whose owner lives in a closed arena, and E0701 (a value escaping its region) is still unfinished. The README marks the whole mode as experimental for that reason.

Experimental means experimental. Stack mode is tested differentially against heap mode and under AddressSanitizer, but the region analysis still has conservative corners. The heap mode remains the default for a reason.
07. Threads

Ownership stops at the thread boundary

The thread API is intentionally small:

threads.yack 
fun worker (id : int64) : unit =
    print_string ("worker " ^ int_to_string (int64_to_int (id)))

fun main () =
    let val thread = sys.thread_spawn (worker, int_to_int64 (1))
        val _ = sys.thread_join (thread)
    in ()
    end

sys.thread_spawn takes a static function of type int64 -> unit and an int64 payload. sys.thread_join returns unit. There are no capturing closures, so a worker has no environment; the only value that crosses the boundary is the int64.

That is also why there is deliberately no Send or Shared type yet. The boundary is already an int64, and no pointer to the Yack heap can be encoded in it. The arena, scratch arena, root reserve and store-root state are all thread-local, so two threads do not share an allocator. The decision is recorded in docs/threads.md.

The raw SQLite handle path in docs/sql.md is the exception that proves the rule: a connection handle is passed as an int64, and that path is explicitly not checked. The owner must keep the connection alive until thread_join. The language does not prove that for you.

08. What it buys

The advantages, with their scope

  • Deterministic frees. There is no collector deciding when memory is reclaimed. A value is dropped at the end of its owner's scope, after a move, or at a branch merge; the ownership analysis decides the placement.
  • No GC pauses. The runtime has no tracing phase. For a command-line tool, a server request or a language server, the cost of memory management is paid at the allocation and free sites the compiler chose.
  • Use-after-move and leaks are compile errors in the checked subset. E0402 catches a use after transfer; E0403 catches a Linear value that is not consumed on a path. The runtime can be checked separately with yack build --debug-alloc, which prints allocations, frees and a final allocs/frees/net summary.
  • No reference cycles from reference counting. Yack does not use reference counting, so the classic refcount cycle leak does not exist. The other side of that coin is that shared cyclic graphs are not expressible in the safe language (see the costs below).
  • No shared mutable Yack heap state across threads. Only an int64 crosses thread_spawn; the allocator state is thread-local. The thread benchmark is run under ThreadSanitizer and AddressSanitizer in test/thread_tsan.sh. The unchecked raw SQLite handle path is the exception, described above.
  • Small native binaries. In the repository's bench/cli_size comparison, the same argument-parsing program is 130,280 bytes with yack build and 92,680 bytes with --trim, against 2,471,820 bytes for the Go build and 1,042,640 bytes for the Rust build with clap. The Yack binary is dynamically linked against libc, libm and libsqlite3; the comparison is about the shipped artefact, not speed.

These are properties of the current implementation, not a blanket “memory safety” claim. Programs that use raw handles, or parts of the runtime that the SSA validator does not model, sit outside the checked subset. The repository labels those boundaries rather than hiding them.

09. What it costs

The difficulties are part of the design

The model is not free, and the repository is candid about where it strains:

  • Annotation burden. Signatures have to say who owns, who borrows and who consumes. Callback types use consume T -> R when the callback takes ownership; a returned borrow needs from when several parameters could be the source. The compiler infers a lot, but the ownership surface is visible in the source. These borrow annotations and explicit copies are exactly the ceremony the types impose; they are the price of checking ownership without a collector, not accidental noise.
  • No capturing closures. Functions can be passed by name or written inline as x => ..., but an inline function cannot capture a local. A local function that captures is lambda-lifted and may only be called directly; using it as a value is E0518. This is the error for a captured base:
closure.yack 
fun main () =
    let val base = 40
        fun add (x) = x + base
        val f = add
    in print_int (f (2))
    end
yack check 
error[E0518]: local function `add` captures variables and cannot be used as a closure
  --> closure.yack:4:17
  |
4 |         val f = add
  |                 ^^^
  = note: Yack has no capturing closures
  = note: a local function is lambda-lifted and only supports direct calls
  = note: a local function without captures can still be used as a value
  = hint: call it directly, e.g. `add (...)`
  = hint: or move it to module level and pass the captures explicitly
  = hint: example: `fun add (capture, argument) = ...`
  • Higher-order code works, within that limit. lib/yack/src/list.yack provides map, filter, foldl, foldr and zip. The functions are specialized by the call target, but a lambda that needs a captured environment cannot be passed.
  • No type classes or interfaces. The standard library uses concrete, specialized names such as sort_int and contains_string instead of a Comparator or Hashable abstraction. yack/map is string-keyed; a generic map would need hash and eq for its key. docs/stdlib.md lists this as a design limit, not an oversight.
  • Shared graphs and cycles are awkward or impossible. Recursive datatypes are fine, but there is no reference counting and no mutation through a borrow. Building a cyclic mutable graph, or sharing one mutable structure between two owners, is outside the current model. The standard library's collections are Affine and thread the value through each operation.
  • Some reads need a copy. A non-Copy field cannot be read through a borrow (E0508). Accessors have to copy the value out or work through an owned value; the standard library exposes string_copy and borrow variants for arrays and maps, but the ergonomics are still being filled in.
  • The learning curve is in the diagnostics. The checker reports stable codes with notes and hints: move this use before the transfer, consume this value on both branches, name the borrow provenance. The rules are learnable, but branch-sensitive ownership and path-sensitive partial moves take practice.
  • Still experimental. Stack mode's region analysis is incomplete; raw SQLite handles are unchecked; the standard library is partial for networking, dates and encodings; there is no pub/private visibility and no open. The README's status table is the current map.
The honest summary. Yack is a way to ask how far ownership can carry an ML without a GC. It does not claim that every program is easier in this model. Programs with shared mutable state or heavy closure use fight the language; programs with clear ownership and explicit resources fit it well.
