Notes de conception · Modèle mémoire · environ 20 minutes

La possession, sans ramasse-miettes.

Yack est une expérience : un petit langage de la famille ML, dont la syntaxe plaît à son auteur par sa simplicité, compilé en code natif via LLVM. Les types affines et linéaires, empruntés au modèle de possession de Rust, remplacent le ramasse-miettes ; la seule cérémonie qui reste est celle que les types imposent.

  • la syntaxe de SML et OCaml
  • les idées de possession de Rust
  • la gestion manuelle de la mémoire en C et C++

01. Le point de départ

Un ML confortable, sans ramasse-miettes

Yack existe parce que son auteur voulait un langage dont la syntaxe lui plaît : sympathique, simple, celle de la famille ML, proche de SML et OCaml, avec let et val, fun, les datatypes, le filtrage par motifs, les modules et les pipes. L'objectif est un langage où l'on se sente comme chez soi, confortable à écrire, avec peu de cérémonie.

Rust montre que la possession peut remplacer un ramasse-miettes : les types affines et linéaires, les déplacements et les emprunts font le travail qu'un collecteur à balayage ferait autrement. Sa syntaxe est toutefois ressentie comme plus verbeuse et plus lourde ; Yack garde les idées de possession et abandonne ce poids. Le modèle mémoire reste vérifié dans le frontend, sur une syntaxe qui reste petite.

La seule cérémonie qui devrait rester est celle que les types imposent : un déplacement quand la possession est transférée, une annotation d'emprunt quand une valeur est lue sans être prise, un appel qui consomme une valeur linéaire. La section sur l'emprunt montre les annotations, et Ce que cela coûte indique où elles se font sentir. Yack est une expérience ; la version 0.2.0 est utilisable et testée, mais elle n'est pas présentée comme prête pour la production.

Aucune collecte cachée à l'exécution. Les valeurs sont déplacées, empruntées et détruites selon la propriété déclarée. Il n'y a ni ramasse-miettes à balayage ni comptage de références ; le compilateur émet du code natif et les informations de possession sont vérifiées avant la génération de code.

Le reste de cette page décrit le modèle tel qu'il existe dans le dépôt, y compris les parties encore rugueuses. Ce n'est pas la spécification d'un langage achevé.

02. Trois propriétés

Copy, Affine, Linear

Chaque type possède une propriété mémoire. Cette propriété détermine si une valeur peut être dupliquée, déplacée une seule fois, ou doit être consommée exactement une fois.

PropriétéRègleExemples dans Yack
Copy Peut être copiée librement. Le passage ne termine pas la liaison d'origine. int, bool, unit, un record déclaré : Copy
Affine Utilisée au plus une fois. Elle peut être déplacée ou détruite ; le compilateur insère la destruction quand le propriétaire sort de portée. Les types utilisateur par défaut, les records, les datatypes, string, les tableaux et les maps
Linear Utilisée exactement une fois sur chaque chemin. Elle ne peut pas être détruite implicitement ; une valeur non consommée est une erreur de compilation. token, db et statement SQLite, les listeners et les flux réseau

Une déclaration peut indiquer la propriété explicitement :

properties.yack 
type point : Copy = { x : int, y : int }
type buffer : Affine = { size : int }
type handle : Linear = { id : int }
type default_affine = { value : int }

fun main () = ()

Ce bloc est un fichier complet et vérifié ; le main vide sert seulement à rendre les déclarations exécutables. Sans annotation, un type utilisateur est Affine. Un composite contenant un composant Linear devient effectivement Linear, et le vérificateur refuse un type déclaré Copy avec des champs non Copy (E3015) ou un type déclaré Affine avec un champ Linear (E3016). yack types file.yack affiche les propriétés déclarées et effectives.

03. Affine en pratique

Un déplacement est un transfert de possession

Affine est la discipline par défaut. Passer une valeur Affine à un paramètre de fonction la transfère : l'appelé en devient propriétaire. L'ancienne liaison est marquée comme déplacée, donc la relire n'est plus permis. Si l'appelé ne transmet pas la valeur, le compilateur place sa destruction à la fin de la portée.

buffer.yack 
type buffer : Affine = { size : int }

fun grow (buffer : buffer) : buffer =
    { size = buffer.size * 2 }

fun main () =
    let val buffer : buffer = { size = 16 }
        val larger = grow (buffer)
    in print_int (larger.size)
    end

buffer est déplacé dans grow. Le paramètre appartient à grow ; la fonction lit son champ Copy et renvoie un nouveau record. L'ancien record est détruit par l'appelé, le nouveau par main. Aucun free explicite n'apparaît dans le source.

Utiliser l'ancienne liaison après le transfert est refusé. Ici la valeur est un jeton Linear, mais la règle de déplacement est la même pour un record Affine :

use_after_move.yack 
fun main () =
    let val ticket = new_token ()
        val _ = consume_token (ticket)
    in consume_token (ticket)
    end
yack check 
error[E0402]: value `ticket` is used after being moved
  --> use_after_move.yack:4:23
  |
4 |     in consume_token (ticket)
  |                       ^^^^^^
  = note: the value was already transferred to another owner
  = hint: move the use before the transfer, or copy the value if its type is Copy

Les déplacements partiels sont suivis eux aussi. Après le déplacement d'un champ de record, le parent existe encore mais cet emplacement n'est plus initialisé ; le réutiliser donne E0402 avec le chemin du champ dans le message. Le backend ne détruit alors que les champs encore possédés.

04. Ressources linéaires

Certaines choses doivent être fermées exactement une fois

Affine signifie « au plus une fois ». Linear signifie « exactement une fois, sur chaque chemin ». Une valeur Affine peut être détruite silencieusement ; une valeur Linear non. C'est la propriété utilisée pour les ressources dont le nettoyage est observable : un jeton, une connexion SQLite, une requête préparée, une socket.

token_ok.yack 
fun main () =
    let val ticket = new_token ()
        val _ = consume_token (ticket)
    in print_int (1)
    end

Oublier la consommation et le programme ne passe plus le typage. L'erreur nomme la valeur et suggère l'appel manquant :

unconsumed.yack 
fun main () =
    let val ticket = new_token ()
    in print_int (1)
    end
yack check 
error[E0403]: linear value `ticket` is never consumed on this path
  --> unconsumed.yack:2:9
  |
2 |     let val ticket = new_token ()
  |         ^^^^^^^^^^^^^^^^^^^^^^^^^
  = note: values with the Linear property must be consumed exactly once on every path
  = note: leaving it alive is rejected instead of freeing it implicitly
  = hint: consume it with `consume_token (ticket)`
  = hint: or move the consumption after the `if`/`case` so every branch reaches it

La linéarité est une propriété de type déclarée, pas un cas particulier réservé à deux primitives. Un record ou un datatype peut être déclaré : Linear, et le vérificateur le suit à travers les branches. La liaison SQLite de lib/sql/src/Sqlite.yack le fait pour db et statement :

lib/sql/src/Sqlite.yack 
(* excerpt from lib/sql/src/Sqlite.yack *)
type db : Linear = { handle : int64 }
type statement : Linear = { handle : int64, owner : (borrow db) option }

fun main () = ()

close consomme un db ; finalize consomme un statement. Oublier l'un ou l'autre sur un chemin donne E0403 ; fermer deux fois ou utiliser une connexion fermée donne E0402. Une requête préparée détient aussi un emprunt de sa base, donc close (db) avant finalize (statement) donne E0501. Les pièges sont figés par test/sql/forgot_finalize.yack, test/sql/forgot_close.yack, test/sql/close_twice.yack et test/sql/close_with_open_stmt.yack, et documentés dans docs/sql.md.

Pas de destructeurs automatiques. Le langage n'a pas de fermeture de style RAII. Le compilateur peut prouver qu'un close ou un finalize a été oublié, mais il ne les exécute pas automatiquement. La documentation SQLite énonce la même limite.

Le paquet réseau utilise le même schéma pour listener et stream dans lib/net/src/Net.yack ; les fonctions sont close_listener et close. La linéarité est ici une discipline portée par des types de handles déclarés : la propriété est vérifiée par la même analyse de possession que les déplacements, pas par un mécanisme d'exécution séparé.

05. Emprunt

Lire sans prendre possession

Déplacer n'est pas toujours ce que l'on veut. Une fonction qui ne fait que lire un record ne devrait pas l'enlever à l'appelant. Yack dispose de borrow pour cela :

borrow.yack 
type account : Affine = { id : int, balance : int }

fun balance_of (value : borrow account) : int =
    value.balance

fun main () =
    let val account : account = { id = 7, balance = 42 }
        val first = balance_of (borrow account)
        val second = balance_of (&account)
        val moved = account
    in print_int (first + second + moved.balance)
    end

borrow account est un emprunt partagé ; il est Copy, donc une fonction peut le recevoir sans consommer le propriétaire. &account est la forme courte de la même expression, et les deux orthographes sont acceptées. Ici le prêt se termine à la dernière utilisation de la valeur empruntée, donc account peut être déplacé ensuite. Ce sont les durées de vie non lexicales (NLL).

Les règles sont volontairement locales :

  • Un opérande d'emprunt doit être un emplacement : une variable locale, ou une chaîne de champs de record et d'indices de tuple enracinée dans l'une d'elles. borrow (f x) donne E0500.
  • Les emprunts partagés peuvent se chevaucher ; un borrow mut est exclusif et entre en conflit avec tout autre emprunt vivant d'un emplacement qui se chevauche (E0502).
  • Déplacer le propriétaire pendant qu'un emprunt est encore vivant donne E0501 ; un emprunt qui s'échappe du let propriétaire de sa source donne E0507.
  • Une fonction qui renvoie un emprunt doit nommer sa provenance avec from (nom de paramètre ou indice à partir de 1) ; une origine absente ou ambiguë donne E0503.

Deux limites comptent pour une image honnête. Lire un champ non Copy à travers un emprunt est actuellement refusé avec E0508 (« cannot read non-Copy field name through a borrow »), donc un accesseur doit copier la valeur ou atteindre le champ par un autre chemin. Et bien que la syntaxe accepte borrow mut, les emprunts mutables restent des copies non aliasées : aucune opération du langage ne mute à travers un emprunt pour l'instant. Les vérifications et les règles de conflit existent ; la mutation à travers elles n'est pas implémentée.

06. Modes mémoire

Tas, arènes et un mode pile expérimental

Yack possède deux modes d'allocation, choisis à la compilation avec --memory=heap (le défaut) ou --memory=stack. Le même source peut être compilé dans l'un ou l'autre ; le mode change l'exécution émise, pas un drapeau d'exécution.

ModeLibération des valeursÉtat
Heap La possession décide quand free est émis. Un bloc arena regroupe les chaînes temporaires. Défaut
arena ... in ... end Ouvre une portée temporaire et la libère à end. En mode heap, seules les chaînes l'utilisent ; les tableaux et les maps gardent leur destruction normale. Disponible dans les deux modes
--memory=stack Chaque activation reçoit une région à bump-pointer ; la région est détruite au retour, et free ne fait rien. Les valeurs qui s'échappent doivent être prouvées sûres, sinon le programme est refusé. Expérimental
arena.yack 
fun main () =
    arena
        val text = "hello" ^ " " ^ "world"
    in
        print_string (text)
    end

La version avec arène existe parce que les concaténations de courte durée sont fréquentes dans le traitement des requêtes. En mode heap, elle évite un malloc et un free par chaîne temporaire ; le bloc est recyclé à end. En mode stack, l'arène de requête fait partie du schéma de régions, et un emprunt dont le propriétaire vit dans une arène ne peut pas s'échapper du bloc (E0703).

Le mode stack est la moitié la plus ambitieuse de l'expérience. Il n'émet aucun malloc, calloc, realloc ou free de la libc pour les valeurs Yack ; les allocations viennent d'une région réservée avec mmap. Le contrat veut que le compilateur prouve qu'une valeur ne survit pas à sa région et refuse le programme plutôt que de retomber sur le tas. Le vérificateur de régions est encore en cours d'achèvement : E0702 couvre les stockages que l'analyse ne peut pas prouver, E0703 un emprunt dont le propriétaire vit dans une arène fermée, et E0701 (une valeur qui s'échappe de sa région) reste inachevé. Le README marque tout le mode comme expérimental pour cette raison.

Expérimental veut dire expérimental. Le mode stack est testé différentiellement contre le mode heap et sous AddressSanitizer, mais l'analyse de régions garde des recoins conservateurs. Le mode heap reste le défaut pour une bonne raison.
07. Threads

La possession s'arrête à la frontière des threads

L'API de threads est volontairement petite :

threads.yack 
fun worker (id : int64) : unit =
    print_string ("worker " ^ int_to_string (int64_to_int (id)))

fun main () =
    let val thread = sys.thread_spawn (worker, int_to_int64 (1))
        val _ = sys.thread_join (thread)
    in ()
    end

sys.thread_spawn prend une fonction statique de type int64 -> unit et une charge utile int64. sys.thread_join renvoie unit. Il n'y a pas de closures capturantes, donc un worker n'a pas d'environnement ; la seule valeur qui traverse la frontière est l'int64.

C'est aussi pourquoi il n'existe volontairement ni type Send ni type Shared. La frontière est déjà un int64, et aucun pointeur vers le tas Yack ne peut y être encodé. L'arène, l'arène de travail, la réserve racine et l'état d'enracinement du store sont tous locaux au thread, donc deux threads ne partagent pas d'allocateur. La décision est consignée dans docs/threads.md.

Le chemin brut des handles SQLite dans docs/sql.md est l'exception qui confirme la règle : un handle de connexion est passé comme un int64, et ce chemin n'est explicitement pas vérifié. Le propriétaire doit garder la connexion vivante jusqu'à thread_join. Le langage ne le prouve pas.

08. Ce que cela apporte

Les avantages, avec leur portée

  • Libérations déterministes. Aucun collecteur ne décide quand la mémoire est récupérée. Une valeur est détruite à la fin de la portée de son propriétaire, après un déplacement, ou à la jonction de branches ; l'analyse de possession décide de l'emplacement.
  • Pas de pauses de GC. L'exécution n'a pas de phase de balayage. Pour un outil en ligne de commande, une requête de serveur ou un serveur de langage, le coût de la gestion mémoire est payé aux sites d'allocation et de libération choisis par le compilateur.
  • Utilisation après déplacement et fuites sont des erreurs de compilation dans le sous-ensemble vérifié. E0402 attrape une utilisation après transfert ; E0403 attrape une valeur Linear non consommée sur un chemin. L'exécution peut être vérifiée séparément avec yack build --debug-alloc, qui affiche les allocations, les libérations et un résumé final allocs/frees/net.
  • Pas de cycles de références dus au comptage. Yack n'utilise pas de comptage de références, donc la fuite classique par cycle n'existe pas. L'autre face de la médaille est que les graphes cycliques partagés ne sont pas exprimables dans le langage sûr (voir les coûts plus bas).
  • Pas d'état de tas Yack mutable partagé entre threads. Seul un int64 traverse thread_spawn ; l'état de l'allocateur est local au thread. Le benchmark de threads tourne sous ThreadSanitizer et AddressSanitizer dans test/thread_tsan.sh. Le chemin non vérifié des handles SQLite bruts est l'exception décrite plus haut.
  • Petits binaires natifs. Dans la comparaison bench/cli_size du dépôt, le même programme d'analyse d'arguments fait 130 280 octets avec yack build et 92 680 octets avec --trim, contre 2 471 820 octets pour la compilation Go et 1 042 640 octets pour la compilation Rust avec clap. Le binaire Yack est lié dynamiquement à libc, libm et libsqlite3 ; la comparaison porte sur l'artefact livré, pas sur la vitesse.

Ce sont des propriétés de l'implémentation actuelle, pas une affirmation générale de « sûreté mémoire ». Les programmes qui utilisent des handles bruts, ou des parties de l'exécution que le validateur SSA ne modélise pas, restent hors du sous-ensemble vérifié. Le dépôt nomme ces frontières plutôt que de les masquer.

09. Ce que cela coûte

Les difficultés font partie de la conception

Le modèle n'est pas gratuit, et le dépôt dit franchement où il peine :

  • Charge d'annotations. Les signatures doivent dire qui possède, qui emprunte et qui consomme. Les types de rappel utilisent consume T -> R quand le rappel prend possession ; un emprunt renvoyé a besoin de from quand plusieurs paramètres pourraient être la source. Le compilateur infère beaucoup, mais la surface de possession reste visible dans le source. Ces annotations d'emprunt et ces copies explicites sont exactement la cérémonie que les types imposent ; c'est le prix d'une possession vérifiable sans collecteur, pas du bruit accidentel.
  • Pas de closures capturantes. Les fonctions peuvent être passées par nom ou écrites en ligne comme x => ..., mais une fonction en ligne ne peut pas capturer une variable locale. Une fonction locale qui capture est lambda-liftée et ne peut être appelée que directement ; l'utiliser comme valeur donne E0518. Voici l'erreur pour un base capturé :
closure.yack 
fun main () =
    let val base = 40
        fun add (x) = x + base
        val f = add
    in print_int (f (2))
    end
yack check 
error[E0518]: local function `add` captures variables and cannot be used as a closure
  --> closure.yack:4:17
  |
4 |         val f = add
  |                 ^^^
  = note: Yack has no capturing closures
  = note: a local function is lambda-lifted and only supports direct calls
  = note: a local function without captures can still be used as a value
  = hint: call it directly, e.g. `add (...)`
  = hint: or move it to module level and pass the captures explicitly
  = hint: example: `fun add (capture, argument) = ...`
  • Le code d'ordre supérieur fonctionne, dans cette limite. lib/yack/src/list.yack fournit map, filter, foldl, foldr et zip. Les fonctions sont spécialisées par la cible d'appel, mais une lambda qui a besoin d'un environnement capturé ne peut pas être passée.
  • Pas de classes de types ni d'interfaces. La bibliothèque standard utilise des noms concrets et spécialisés comme sort_int et contains_string plutôt qu'une abstraction Comparator ou Hashable. yack/map est indexé par chaîne ; une map générique aurait besoin de hash et eq pour sa clé. docs/stdlib.md présente cela comme une limite de conception, pas comme un oubli.
  • Les graphes partagés et les cycles sont maladroits ou impossibles. Les datatypes récursifs ne posent pas de problème, mais il n'y a ni comptage de références ni mutation à travers un emprunt. Construire un graphe cyclique mutable, ou partager une structure mutable entre deux propriétaires, sort du modèle actuel. Les collections de la bibliothèque standard sont Affine et font circuler la valeur à chaque opération.
  • Certaines lectures exigent une copie. Un champ non Copy ne peut pas être lu à travers un emprunt (E0508). Les accesseurs doivent copier la valeur ou travailler sur une valeur possédée ; la bibliothèque standard expose string_copy et des variantes d'emprunt pour les tableaux et les maps, mais l'ergonomie est encore en cours de comblement.
  • La courbe d'apprentissage passe par les diagnostics. Le vérificateur rapporte des codes stables avec notes et indices : déplacer cette utilisation avant le transfert, consommer cette valeur sur les deux branches, nommer la provenance de l'emprunt. Les règles s'apprennent, mais la possession dépendante des branches et les déplacements partiels dépendants des chemins demandent de la pratique.
  • Toujours expérimental. L'analyse de régions du mode stack est incomplète ; les handles SQLite bruts ne sont pas vérifiés ; la bibliothèque standard est partielle pour le réseau, les dates et les encodages ; il n'y a ni visibilité pub/privée ni open. La table d'état du README est la carte actuelle.
Le résumé honnête. Yack est une manière de demander jusqu'où la possession peut porter un ML sans GC. Il ne prétend pas que tout programme est plus simple dans ce modèle. Les programmes à état mutable partagé ou à usage intensif de closures luttent contre le langage ; les programmes à possession claire et ressources explicites s'y prêtent bien.
